# anyHelper style guide — the porting rubric

The helper is a hand-curated, agent-ergonomic surface over the `any`
REST API (ADR plan §4 "anyHelper: curated surface"). It is NOT
autogenerated: it encodes real discovery about how an LLM wants to call
things. This guide is the rubric for porting the old JS anyHelper to
Python facades and for the drift skill's "does this match our idiom"
check. Every convention below earned its place by biting us.

## 1. Naming & surface

- **snake_case, verb-first, Pythonic** — `create_object`, `update_object`,
  `get_object`, `list_spaces`, `query`, `search`. Not the JS
  camelCase, not the raw REST paths.
- **One facade per conceptual operation**, not per endpoint. A facade
  may bundle several HTTP calls (create + set markdown) when that is
  the natural unit — the helper is where aggregation is allowed (the
  server keeps 1:1 endpoint↔SDK; the helper is the ergonomic layer).
- **Return values are plain dicts / dataclasses**, never raw responses.
  Reads come back in the nested read shape (§3); writes return the
  created/updated id + a normalized result.

## 2. Errors: normalized, never silently swallowed

- **No silent drops.** The single worst class of bug: a misplaced key
  ignored while returning success (bobrik once created 8 objects with
  ZERO properties while seeing ok:true, from a bad skill example). Any
  unrecognized top-level data key must RAISE, not be dropped.
- Map `{error:{code,message}}` envelopes to typed exceptions
  (`AnyError(status, code, message)` — already in anyclient); the
  helper adds operation context, never leaks paths/SDK internals.
- Validation failures surface with the server's hint (e.g.
  `property.not_found` lists valid props) — pass it through.

## 3. The nested type-group shape (reads AND writes mirror)

Properties live at `record[typeId][propId]`. The helper hides the
CID plumbing behind readable keys:

```python
create_object("book", {"name": "Dune", "book": {"author": "Herbert", "year": 1965}})
update_object(oid, {"book": {"rating": 9}})
obj["book"]["author"]           # reads mirror the write shape
```

- **Writes key by propId, resolved from a readable xKey** via the
  catalog (§4). Writing by xKey directly → `property.not_found`. The
  helper does the xKey→propId resolution; callers never see propIds.
- **Reserved top-level keys**: `name`, `body`/`markdown`, `types`,
  `space`. Every other top-level key MUST resolve to a type
  xKey/id (a `{prop: value}` group) or the call raises (§2 — closes
  the silent-drop hole).
- Dotted `"type.prop"` paths are READ syntax only (filter, sort,
  get_prop) — never write keys.

## 4. Catalog & resolution (cached per resolved space)

- The helper keeps a per-space **catalog**: type xKey/name → typeId,
  and per-type propId ↔ xKey maps (`GET /types`, `GET
  /types/:id/properties` → `[{id,name,xKey,kind}]`).
- **Cache keyed by RESOLVED spaceId**, TTL-bounded, invalidatable — a
  cross-space call must not read another space's catalog.
- Conceptual keys (user xKeys such as `"program"`) resolve to real
  ids through the catalog. The built-in registered types have literal
  string ids (`"page"`, `"miniapp"`, `"bin"`, `"dataview"`); user
  types (including `program` / `mini_app`) have `bafyrei…` hashes. A
  dataset is named by its store KEY and resolved to the server's
  collection against the host object's types (ADR-027 §2).

## 5. Space handling

- Every facade takes an optional `space` param (a spaceId or an alias
  the helper resolves); default = the current/agent space. This is the
  cross-space generalization (arbitrary spaceId scope) — the single
  resolution point, catalog cached per resolved space.

## 6. Wire-format landmines (from any-api-gotchas — bake into the port)

- `editor/editor_blocks/markdown` uses `{"content": ...}`, NOT
  `{"markdown": ...}`; the object must carry `page` (or a type with a
  shared editor part) first.
- `POST /types` returns `{"typeId": ...}`, NOT `{"id": ...}`.
- Property creation uses `kind` for the value shape and `xFormat`
  (`{"type": <slug>, …}`) for dates/relations/choices (ADR-027 §4) —
  there is no `format` or `xKind` — and `xKey` (not `key`).
- Registered handler types (`program`, `chat`, …) REJECT
  `POST /types/:id/properties` (500) — properties statically declared;
  only user types accept dynamic props.
- Deleted spaces persist in `GET /spaces` with `status:"deleted"` —
  filter by status on name lookups.
- `objects/query` filter `{"any.types": "<typeId>"}` needs the real
  typeId (resolve via catalog), not a conceptual key.
- **NUL sanitization** at every dataset write (anyenc/fastjson can't
  take `\x00` — anyclient.sanitize_nuls, already wired).

## 7. What the port must NOT carry over

Through the workaround/skill audit (plan §4): old-anytype fossils,
Sobek-specific quirks (die with the runtime), and harness-design
guidance invalidated by v2. Provenance-tag each convention; a
workaround ports only with a test proving it is still needed. When a
quirk is really an `any` bug, fix upstream (dated bridge + ticket),
don't carry the workaround.

## 8. The shrinking-layer principle

anyHelper is a shrinking layer by intent: its ergonomic discoveries
are requirements for evolving the REST API itself. Where a convention
here exists only to paper over an awkward endpoint, that is an upstream
issue, and over time the API absorbs the ergonomics and the helper
thins toward passthrough.
